# Agentwheel Project Notes

## Project Context

Agentwheel is a TypeScript CLI for installing OpenPack artifacts into multiple AI agent harnesses.
It manages skills, instructions, rules, commands, MCP, hooks, settings, plugin artifacts, and custom
adapter targets through planned installs and manifests.

Prefer small, focused changes that preserve deterministic planning, manifest safety, and documented
harness behavior.

## Commands

- Install dependencies: `pnpm install`
- Typecheck: `pnpm typecheck`
- Test: `pnpm test`
- Build: `pnpm build`
- Prepare release metadata from `package.json`: `pnpm release:prepare <stable-semver>`
- Check every derived release copy: `pnpm release:check`

Run `pnpm typecheck` and `pnpm test` before release commits. Run `pnpm build` when changing CLI
runtime behavior or version metadata so `dist/index.js` reflects the release.

## Architecture Rules

- Use existing module boundaries under `src/model`, `src/install`, `src/lifecycle`, `src/runtime`,
  `src/staging`, and `src/adapters`.
- Prefer structured schemas and typed helpers over ad hoc path/string handling.
- Install planning must remain deterministic, idempotent, and drift-safe.
- Runtime output directories are generated by Agentwheel; do not hand-edit them to fix tests.
- Keep generated state partitioned when target identity can differ. Adapter, installation type, and
  target fingerprint must not collide.

## Artifact Compatibility

- Built-in harness behavior must be based on documented native paths, not inferred folder names.
- The user-facing scoping concept is `installationType`; do not introduce vague `path` or `project`
  concepts.
- Keep `installationType` values open strings. `local` and `user` are defaults, not the full model.
- Unsupported or undocumented mappings should fail clearly and be documented in the compatibility
  matrix.
- Update `docs/design/artifact-harness-compatibility.md` and tests when changing harness mappings.

Important current mappings and semantics:

- Codex local skills use `.agents/skills`; user skills use `~/.agents/skills`.
- Do not install Codex skills into `.codex/skills`.
- Codex rules are command execution policy rules, not general behavioral instructions.
- Claude local skills use `.claude/skills`; user skills use `~/.claude/skills`.
- Claude rules are behavioral/path-scoped instructions.
- Claude MCP project config is `.mcp.json`, not `.claude/.mcp.json`.
- Copilot skills default to `.github/skills` and `~/.copilot/skills`; `.agents/skills` is only a
  documented alternative, not the default.
- OpenClaw local skills default to workspace `skills/`; user/global skills use `~/.openclaw/skills`.
- Hermes skills support user install only by default; local Hermes skills are unsupported unless an
  explicit configured adapter documents that behavior.

## Tests

- Add path-resolution coverage for every supported-native mapping.
- Add negative tests for known wrong mappings when fixing compatibility issues.
- Use temp dirs for install smoke tests and assert exact installed layout plus manifest partitioning.
- Keep manual smoke scripts generic; do not use private customer/project names as fixtures.

## Release And Publish

- Do not run `npm publish` manually from Codex or other local agents.
- The npm package publish is handled by the configured release pipeline.
- For a release, run `pnpm release:prepare <stable-semver>`, replace any generated changelog
  placeholder with real notes, and run `pnpm release:check`. `package.json.version` is the only
  manually maintained product-version source; OpenPack, product skills, site markers, and the
  changelog heading are derived or checked.
- Run `pnpm typecheck`, `pnpm test`, and `pnpm build` before pushing release changes.
- A `package.json` version increase merged to `main` is validated by the auto-release workflow. It
  creates the annotated tag and dispatches the release pipeline only when all version files and the
  changelog agree and the tag/npm version do not already exist.
- Do not push a release tag manually during the normal flow. Use the release workflow's manual
  dispatch only to recover an existing tag whose publish run did not complete.
- If npm auth is missing locally, treat that as expected; do not try to re-authenticate or publish
  outside the pipeline unless a maintainer explicitly asks for a manual emergency publish.

## Git Safety

- Do not revert unrelated user changes.
- Inspect `git status -sb` before staging.
- Stage intentionally. Use `git add -A` only when the user explicitly asks to include everything.
- Avoid force pushes unless the user explicitly approves the exact branch and reason.
